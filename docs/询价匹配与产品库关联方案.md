# 询价匹配与产品库关联方案

> 最后更新：2026-10-28
> 涉及页面：`/inquiry-match`（询价匹配）、`/goods`（产品管理）、`/sales`（销售查询）
> 涉及表：`part_inquiries`、`sales_inquiry_listing_status`、`parts`，以及 OA 库三张表

## 一、目标

把 `/inquiry-match` 做成询价处理的唯一工作台：

1. OA 里完成的询价自动进入匹配页，不需要人工去找。
2. 匹配到产品库 SPU/SKU 后，这条询价自动下架，`/sales` 的「来自询价记录」维度不再出现，只能从对应产品详情里看到这条询价。
3. 产品库里找不到能匹配的产品时，从匹配页跳到 `/goods` 的新增产品表单，把询价信息带过去预填，新增完回到匹配页完成关联。
4. 确认不需要匹配的询价，在匹配页下架，不影响 OA 数据。

## 二、现状（改造前）

### 数据规模

| 项 | 数量 |
|---|---|
| OA 完成的询价任务（`mission_type=1`、`mission_status=4`、未软删） | 4099 |
| 已匹配（`part_inquiries.part_id` 非空） | 1 |
| 其中关联商品已被软删 | 20 |
| 其中关联商品已作废（`invalid_state<>0`） | 1610 |
| OA 产品库 SPU | 5315 |

### 表

`part_inquiries`（本地库，启动时幂等建表）

| 字段 | 说明 |
|---|---|
| `inquiry_mission_id` | OA 询价任务 ID，唯一键 |
| `part_id` | 关联 SPU，NULL 表示未匹配 |
| `variant_group_id` | 关联 SKU |
| `matched_by` / `matched_at` | 核对人和时间 |

`sales_inquiry_listing_status`（本地库，手工建，项目里没有建表脚本）

| 字段 | 说明 |
|---|---|
| `inquiry_mission_id` | 主键 |
| `listing_status` | 1 上架，0 下架 |
| `reason` / `updated_by` | 下架原因和操作人 |
| `feedback_id` | 关联销售反馈，下架时顺手把反馈标记完成 |

OA 库三张表都有 `delete_time`（逻辑删除），任务表另有 `mission_status`，商品表另有 `invalid_state`（作废）。

### 相关接口

| 接口 | 作用 |
|---|---|
| `GET /api/inquiry-match/records` | 匹配页列表，现按 `part_id` 分全部/待匹配/已匹配 |
| `GET /api/inquiry-match/products` | 按分类查产品 |
| `POST /api/inquiry-match/save` | 保存匹配关系 |
| `PATCH /api/inquiries/{id}/listing-status` | 下架/恢复，写 `sales_inquiry_listing_status` |
| `GET /api/inquiries` | `/inquiries` 页面列表，含上下架 tab 和销售反馈 |
| `GET /api/sales/products` | 销售查询，合并配件库和询价两个来源 |
| `POST /api/products` | 新增产品主表，返回带 id 的 product |

`/sales` 过滤已下架询价的做法是：`sales.py` 的 `_hidden_inquiry_mission_ids()` 读出 `listing_status=0` 的 id，在 OA 查询里用 `m.id NOT IN (...)` 排除。

## 三、目标数据流

```
OA 询价完成
   ↓
/inquiry-match 待匹配
   ├─ 找到产品 → 保存匹配 → 自动下架 → /sales 询价维度消失，产品详情里可见
   ├─ 找不到产品 → 跳 /goods 新增（带询价信息）→ 回匹配页关联
   └─ 不需要匹配 → 手工下架 → 进「不需要」tab，可恢复
```

## 四、核心设计决策

| 决策 | 结论 | 原因 |
|---|---|---|
| 是否写 OA 库的 `delete_time` | 不写 | OA 账号是只读用途，写它会影响 OA 自己的询价列表、采购统计、对账。风险与收益不成比例 |
| 下架状态存哪 | 复用 `sales_inquiry_listing_status` | 表已存在，字段够用（有原因和操作人），`/sales` 已按 `listing_status=0` 过滤，前端接口现成 |
| 是否给 `part_inquiries` 加 `ignored_at` | 不加 | 上一版方案的设计，复用下架表后这套字段和两个新接口全部取消 |
| 匹配成功是否自动下架 | 是 | 一处写入，`/sales` 自动生效，不需要在 `_hidden_inquiry_mission_ids()` 里再 UNION `part_inquiries` |
| 匹配页是否建回收站 | 不建独立页面，用「不需要」tab | `/inquiries` 页面保留，两边看的是同一张表 |
| 新增产品是否内嵌表单 | 不内嵌，跳 `/goods` | 新增涉及规格、组合、供应商价格，匹配页做一半的表单只会变成半成品产品编辑器 |
| 是否做批量下架 | 暂不做 | 误操作代价高，且待匹配量大的根因是没有对应产品，不是操作效率 |
| 是否迁移销售反馈处理 | 暂不迁移 | `/inquiries` 页面先保留，等完全不需要处理询价时再决定 |

## 五、改动清单

### 后端

**1. `parts_system/model/migration.py`**

补 `ensure_sales_inquiry_listing_status_table()`，用 `CREATE TABLE IF NOT EXISTS`，在 `database.py` 里跟 `ensure_part_inquiries_table` 一起调用。线上如果已有这张表，先把 `SHOW CREATE TABLE` 的输出对一遍，避免索引不一致。

**2. `parts_system/routes/inquiry_match.py`**

- `list_match_records`：除 `_match_map()` 外再读一次 `sales_inquiry_listing_status` 的 map，每条记录带上 `listing_status`。tab 判定改成：

| tab | 条件 |
|---|---|
| 全部 | 不过滤 |
| 待匹配 | `part_id` 为空，且 `listing_status<>0` |
| 已匹配 | `part_id` 非空 |
| 不需要 | `part_id` 为空，且 `listing_status=0` |

`stats` 从三个字段变四个：`all`、`pending`、`matched`、`dismissed`。

- `save_match`：匹配成功后写一次下架。独立 try/except，失败只记 warning，不回滚匹配。

```sql
INSERT INTO sales_inquiry_listing_status
    (inquiry_mission_id, listing_status, reason, updated_by)
VALUES (%s, 0, '已关联产品库', %s)
ON DUPLICATE KEY UPDATE
    listing_status=0, reason=VALUES(reason),
    updated_by=VALUES(updated_by), updated_at=NOW()
```

- `save_match` 的 OA 校验、`detail` 的查询：都补 `delete_time IS NULL`，避免对已删除的询价任务继续操作。

**3. `parts_system/routes/inquiries.py`**

`_fetch_oa_inquiries` 的 join 补 `AND g.delete_time IS NULL`，排除商品已软删的 20 条。

**4. `parts_system/routes/sales.py`**

- `_fetch_inquiry_products` 的 join 同样补 `AND g.delete_time IS NULL`。
- 新增 `GET /api/sales/parts/{part_id}/inquiries`：先查 `part_inquiries` 拿 mission id 和 `matched_at`，再用一次 `IN` 去 OA 取商品名、规格、品牌、报价、更新时间。不分页。

### 前端

**5. `templates/inquiry-match.html` + `static/js/inquiry-match.js`**

- tab 从三个变四个，加「不需要」。
- 待匹配的卡片加「下架」按钮，文案用「下架」而不是「删除」，和 `/inquiries` 页面保持一致。确认用原生 `confirm()`，不加自定义弹窗。
- 「不需要」的卡片加「恢复」按钮。
- 产品搜索区加「没有合适的，新增产品」按钮。

**6. `/goods` 新增产品预填**

匹配页跳转：`/goods?create=1&from_inquiry=<mission_id>`

`products.js` 现有的 `?create=1` 逻辑（打开新增表单）扩展为：检测到 `from_inquiry` 时，拉 `/api/inquiry-match/detail/<id>`，预填这些字段：

| 表单字段 | 来源 |
|---|---|
| `product_name` | 询价商品名称 |
| `model` | 询价规格型号 |
| `product_brand` | 询价厂家 |
| `key_part_images` | 询价图片 |
| `purchase_cost` | 询价采购报价 |

三级分类不预填，询价里没有可靠分类信息，由用户手选（必须选自分类树）。

新增成功后，如果来自匹配页，跳回 `/inquiry-match?mission=<id>&part=<new_part_id>`。匹配页读取参数后选中那条询价和那个产品，提示用户确认规格后点保存完成关联。不自动保存，产品刚建出来可能还没有规格组合。

**7. `/sales` 详情展示关联询价**

`sales.html` 在沟通记录区块上方加「关联询价记录」区块，配件库来源且有数据时才显示，样式复用现有的 `.sales-detail-table-wrap`。`sales.js` 打开详情时按 `part_id` 拉一次。

## 六、页面交互串联

| 场景 | 操作路径 |
|---|---|
| 正常匹配 | 匹配页选记录 → 选分类 → 选产品 → 选 SKU → 保存 → 记录进「已匹配」，`/sales` 询价维度消失 |
| 产品库没有 | 匹配页点「新增产品」→ `/goods?create=1&from_inquiry=` → 填完保存 → 跳回匹配页 → 确认关联 |
| 不需要匹配 | 匹配页点「下架」→ 记录进「不需要」→ `/sales` 不展示 |
| 误下架 | 匹配页「不需要」tab 点「恢复」，或去 `/inquiries` 的已下架 tab 恢复 |
| 销售查历史 | `/sales` 搜产品 → 详情里看到关联过的询价 |

## 七、边界与已知问题

| 问题 | 现状 | 处理 |
|---|---|---|
| 线上可能没有 `sales_inquiry_listing_status` | 代码里对 1146 做了容错，返回 503「请先执行询价上下架SQL脚本」 | 上线前先 `SHOW TABLES` 确认，补齐迁移脚本 |
| `reason` 会被覆盖 | 写入口的 upsert 是 `reason=VALUES(reason)`，没做 `COALESCE` | 匹配页下架时固定传 `reason`，不改现有 SQL |
| 已匹配的产品后来下架 | 配件库列表不显示（`parts.status=1` 过滤），询价也已下架，`/sales` 两个维度都查不到 | 暂不处理。需要时在 `_hidden_inquiry_mission_ids()` 里改成只隐藏「已匹配且在架」的记录 |
| 作废商品（`invalid_state<>0`）有 1610 条 | 代码完全没管这个字段 | 暂不处理。是否要排除得看业务口径，作废询价的历史价可能还有参考价值 |
| `listing_status=0` 有两种来源 | 手工下架和匹配自动下架写同一列 | 匹配页靠 `part_id` 是否为空区分，不改表结构 |
| 新增产品预填价格后 `/sales` 仍显示空价 | 销售价来自 `product_variant_prices`（规格级），不是 `parts.purchase_cost` | 预填只写成本价，价格要在 `/goods` 配完规格后补 |

## 八、验收清单

1. 匹配页四个 tab 能切换，统计数字互相对得上（`all = pending + matched + dismissed`）
2. 保存一条匹配后，记录从「待匹配」进「已匹配」，`stats.matched` 加 1
3. 该记录在 `/sales` 的「来自询价记录」里消失，在产品详情里能看到
4. 匹配页下架一条待匹配记录，进「不需要」，`/sales` 不显示，「恢复」后回到待匹配
5. 下架时带的 `reason` 在 `/inquiries` 的已下架 tab 能看到
6. 匹配页点「新增产品」，`/goods` 表单里名称、型号、品牌、图片、成本价已预填
7. 新增保存后跳回匹配页，询价和产品已选中，点保存能建立关联
8. 已删除的询价任务（`delete_time` 非空）查详情返回 404，保存匹配也返回 404
9. 商品已软删的 20 条不再出现在匹配页和 `/sales`
10. 重复保存同一条匹配，不产生重复记录，下架状态不报错

## 九、上线注意

1. 先查线上表是否存在，再决定迁移是否需要执行 DDL。
2. 本次无破坏性库变更，`part_inquiries` 不变，`sales_inquiry_listing_status` 只补建表。
3. `/goods` 和 `/inquiry-match` 的 JS、CSS 引用都带版本号，改动后记得递增，避免浏览器缓存。
4. 上线后先验证第 2、3 条，这是本次改动的核心链路。
