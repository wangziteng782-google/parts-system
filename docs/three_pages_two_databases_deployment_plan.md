# 三页面、双数据库与分阶段部署方案

## 1. 已确认事项

当前系统最终为一个FastAPI项目、一个服务端口、三个页面：

```text
数据批改页：/parts/editor
销售价格与询价参考页：/parts/sales
员工工作日志页：/parts/logs
```

线上正式项目通过统一入口把用户带入本系统。Token中可以解析出：

- 线上用户ID；
- 当前用户权限。

线上询价参考信息根据以下两个字段查询：

```text
产品名称 + 产品型号
```

销售页面商品价格根据 `parts_database` 当前成本价乘统一比例，由后端计算。

系统连接两个数据库：

```text
parts_database
  → 产品、图片、规格组合、供应商成本价、工作日志
  → 批改页面可以读写

线上业务数据库
  → 线上询价参考、线上用户基础信息
  → 本系统只读
```

`parts_database` 将随应用部署到服务器，线上业务数据库保持原有位置。

## 2. 统一入口和权限

建议入口：

```text
POST /api/auth/entry
```

请求包含：

```text
token
target_page：editor、sales、logs
```

后端必须验证Token签名、过期时间和签发方，不能只Base64解码内容。
验证成功后取得用户ID和权限，建立本系统短期 `HttpOnly` Cookie，再跳转页面。

权限示例：

| 权限 | 批改页 | 销售页 | 日志页 |
|---|---:|---:|---:|
| 管理员 | 是 | 是 | 是 |
| 批改员工 | 是 | 是 | 按需要 |
| 销售员工 | 否 | 是 | 否 |

接口权限必须在后端验证，不能只隐藏页面按钮。

## 3. 用户和工作日志

本系统不再维护独立登录密码。线上用户表只复制本系统需要的字段，例如：

```text
用户ID
账号
姓名
状态
同步时间
```

操作日志使用Token解析出的线上用户ID。

日志只记录：

- 新增产品；
- 修改产品、规格、供应商价格和图片。

日志用于：

- 统计员工今日新增数量；
- 统计员工本月新增数量；
- 展示某个产品几点由谁修改了什么。

登录、查询和删除不记入工作日志。

## 4. 销售价格页面

销售页只读，页面风格与当前批改系统一致。

查询过程：

```text
1. 从parts_database读取产品、图片、规格组合和当前成本价
2. 取得产品名称和产品型号
3. 从线上数据库精确查询对应询价记录
4. 后端计算销售展示价格
5. 合并为销售页面响应
```

线上询价查询原则：

- 产品名称和型号都去除前后空格；
- 两个字段都有值时才执行精确查询；
- 型号为空时不自动只按产品名称匹配，避免展示错误询价；
- 查询到多条记录时按询价时间倒序展示；
- 页面明确标注“询价参考”，不能覆盖当前成本数据。

销售展示价格：

```text
展示价格 = 当前成本价 ×（1 + 配置比例）
```

统一比例放服务器环境变量：

```env
SALES_PRICE_MARKUP_RATE=0.20
```

后端使用Decimal计算并统一保留两位小数。销售接口只返回换算后的展示价格，
不返回原始成本价。

规格组合已选择供应商时，优先使用：

```text
product_variant_prices.purchase_cost
```

没有规格供应商成本时，再根据最终确认规则决定是否回退到：

```text
parts.purchase_cost
```

## 5. 双数据库连接

应用配置两个独立连接池和数据库账号：

```env
PARTS_DATABASE_URL=...
ONLINE_DATABASE_URL=...
```

- `parts_database`账号授予业务所需的读写权限；
- 线上数据库账号只授予SELECT；
- 两个数据库不执行跨库写事务；
- 线上数据库不可用时，批改页面仍应可以使用本地业务数据；
- 销售页面显示“询价参考暂时不可用”，不能拖死全部系统。

## 6. 推荐部署策略

采用两阶段部署。

### 阶段一：现在做最小化测试部署

目的不是上线业务，而是提前验证服务器环境。

测试范围：

1. 在服务器安装Python运行环境和项目依赖；
2. 部署当前项目副本；
3. 导入 `parts_database_test` 测试数据库；
4. 使用只读账号测试线上数据库 `SELECT` 连通性；
5. 使用一份真实脱敏Token验证用户ID和权限解析；
6. 配置Nginx测试路径和静态资源；
7. 验证七牛图片访问及上传网络；
8. 验证服务器时区、MySQL字符集和中文数据；
9. 验证服务重启、控制台日志和数据库备份。

测试地址应与正式入口隔离，例如：

```text
https://正式域名/parts-test/
```

测试部署不连接正式可写业务库，不开放给普通员工使用。

### 阶段二：功能完善后正式部署

完成以下内容后再正式切换：

1. Token入口和三页面权限；
2. 数据批改页回归；
3. 销售价格和线上询价查询；
4. 工作日志写入、统计和产品时间线；
5. 双数据库超时和异常降级；
6. 正式 `parts_database` 备份及迁移；
7. 正式环境配置和只读账号；
8. 页面及接口验收。

正式部署使用带日期和版本号的发布目录，保留上一版本用于代码回滚。

## 7. 为什么现在先测试部署

测试部署可以提前发现：

- Windows本地路径和Linux服务器路径差异；
- Python和依赖版本不兼容；
- Nginx前缀导致静态资源404；
- Token签名算法或字段理解不一致；
- Cookie、跨域或嵌入页面问题；
- 服务器无法访问线上数据库；
- MySQL版本、排序规则和时区不一致；
- 七牛网络、目录权限或环境变量问题。

这些问题如果等三个页面全部完成后才发现，会同时影响大量已完成代码。
因此推荐“现在验证部署链路，功能完成后再正式上线”，不建议现在直接正式上线，
也不建议完全开发完成后才第一次接触服务器环境。

## 8. 测试部署前需要的资料

1. 服务器操作系统、IP和登录方式；
2. 正式项目对本系统使用的域名或反向代理路径；
3. Token签名算法、密钥或公钥、有效期及字段样例；
4. 用户ID和权限字段名称；
5. 线上询价数据库地址及只读账号；
6. 询价表名、产品名称字段、产品型号字段和询价时间字段；
7. 测试环境销售加价比例；
8. 是否通过页面跳转、菜单链接或iframe打开本系统。
